Политика релизов Apache Airflow
Перед выбором целевой версии Apache Airflow необходимо учитывать официальную политику релизов проекта. Начиная с версии 2.0.0 используется семантическая схема нумерации X.Y.Z, где
•	X — номер мажорной версии
•	Y — номер минорной версии (новая функциональность в рамках обратной совместимости)
•	Z — номер патч-релиза (исправления дефектов и уязвимостей с незначительными изменениями). 
Изменение X указывает на потенциально обратно несовместимые изменения (например, переход с ветки 2.x на 3.x). Изменение Y соответствует расширению функциональности при сохранении совместимости в пределах мажорной ветки. Изменение Z отражает точечные исправления и обновления безопасности и, как правило, не предполагает существенных изменений поведения системы.
В рамках минорной ветки релизы с увеличением Z (патч-релизы) в соответствии с принятой моделью SemVer предназначены прежде всего для исправления дефектов и обновлений безопасности, а также для ограниченных функциональных корректировок, не меняющих базовую совместимость ветки. По этой причине при прочих равных условиях более поздний патч-релиз рассматривается как более зрелая и предпочтительная точка внедрения внутри одной и той же минорной версии.
Одновременно необходимо учитывать, что любое исправление может приводить к регрессиям и появлению новых дефектов, поэтому вывод о зрелости версии должен подтверждаться фактическими метриками качества (статус дефектов, критичность, динамика закрытия, длительность эксплуатации). Дополнительно следует учитывать платформенные ограничения совместимости: для актуальных веток Airflow 3.x требуется Python версий 3.10-3.13.

Методология балльной оценки версий

Для количественного обоснования выбора целевой версии применялась балльная модель оценки на основе метрик GitHub-репозитория apache/airflow. Данные по дефектам собирались методом анализа временны́х окон релизов (release-date-window): для каждой ветки учитывались issue с меткой kind:bug, зарегистрированные в период от выхода первого релиза ветки до даты выхода следующего минорного релиза (или до даты оценки для актуальной ветки). Дата сбора данных — 09.04.2026.

Система оценки включает пять критериев, каждый оценивается по шкале 0–2 балла (максимальная сумма — 10 баллов). Предусмотрено блокирующее правило: три и более открытых критических дефектов по критерию К1 исключают версию из рассмотрения вне зависимости от суммарного балла.

	К1. Открытые критические дефекты (priority:critical, state:open):
		0 дефектов  — 2 балла
		1–2 дефекта — 1 балл
		≥3 дефектов — 0 баллов (блокировка)

	К2. Доля закрытых дефектов (closed/total для label:kind:bug):
		≥85%        — 2 балла
		75–84%      — 1 балл
		<75%        — 0 баллов

	К3. Зрелость патч-серии (количество патч-релизов ветки):
		≥8 релизов  — 2 балла
		3–7 релизов — 1 балл
		0–2 релиза  — 0 баллов

	К4. Период открытой эксплуатации (дней со дня выхода первого релиза ветки до даты оценки):
		≥180 дней   — 2 балла
		30–179 дней — 1 балл
		<30 дней    — 0 баллов

	К5. Статус поддержки (на дату оценки):
		Полная поддержка         — 2 балла
		Ограниченная поддержка   — 1 балл
		Снята с поддержки        — 0 баллов

Подготовка исходных данных

Для сбора исходных данных использовался инструмент GitHub CLI (gh), выполняющий запросы к GitHub Search API по репозиторию apache/airflow. Для каждой сравниваемой ветки применяются одинаковые шаблоны команд; изменяются только временное окно анализа в формате <DATE_FROM>..<DATE_TO> и маска версии <MAJOR>.<MINOR>.

Примечание: применяемый метод временны́х окон не обеспечивает стопроцентной точности в отнесении дефектов к конкретной версии — issue могут быть зарегистрированы с задержкой, переоткрыты, перемечены или относиться к нескольким веткам одновременно. Тем не менее данный подход является наиболее воспроизводимым из доступных без прямого аудита каждого issue, и его систематическое применение ко всем веткам обеспечивает сравнимость результатов в рамках настоящей оценки.

1. Сбор исходных показателей

Даты релизов ветки:
gh release list --repo apache/airflow --limit 100 --json tagName,publishedAt

Всего зарегистрированных дефектов:
gh api "search/issues?q=repo:apache/airflow+is:issue+label:kind:bug+created:<DATE_FROM>..<DATE_TO>&per_page=1" --jq ".total_count"

Открытых дефектов:
gh api "search/issues?q=repo:apache/airflow+is:issue+label:kind:bug+created:<DATE_FROM>..<DATE_TO>+is:open&per_page=1" --jq ".total_count"

Открытых критических дефектов:
gh api "search/issues?q=repo:apache/airflow+is:issue+label:kind:bug+created:<DATE_FROM>..<DATE_TO>+label:priority:critical+is:open&per_page=1" --jq ".total_count"

Количество выпусков ветки:
определяется по результату команды получения дат релизов как количество найденных релизов в рамках выбранной ветки.

Статус поддержки ветки:
определяется по официальной странице Apache Airflow в разделе Version Life Cycle и по факту выхода более нового минорного релиза.

Интерпретация результатов:
•	3.0.x (7/10): несмотря на наибольший суммарный балл, последний патч вышел 29.08.2025 (3.0.6) и дальнейших выпусков не предвидится. Внедрение выглядит не логичным с учетом временного окна, которое будет затрачено на подготовку к переносу этой версии
•	3.1.x (6/10, заблокировано): ветка лишается права на рассмотрение по блокирующему правилу вследствие трёх открытых критических дефектов (подробности — выше). Внедрение не рекомендуется, до исправления в последующем(их) патче(ах).
•	3.2.0 (4/10): актуальная стабильная версия, критических дефектов (пока) не выявлено. Вместе с тем ветка существует 2 дня, не прошла ни одной патч-итерации; надёжная оценка стабильности невозможна.

Заключение: ни одна из рассмотренных версий не соответствует критериям зрелого внедрения в продуктивную среду на дату оценки 09.04.2026. Рекомендуется отложить внедрение до выхода первых патч-релизов ветки 3.2.x и последних для ветки 3.1.х и проведения повторной балльной оценки. В случае необходимости принятия решения в данный момент, то рекомендуемой версией для внедрения является 3.0.6. (см. приложение)

Краткое резюме
В рамках аналитической оценки выполнен сбор релизных и дефектных метрик по данным официального репозитория Apache Airflow (GitHub API) с применением единой методики по временным окнам, а также проведена балльная оценка по критериям критичности дефектов, динамики закрытия, зрелости патч-серии, периода эксплуатации и статуса поддержки.

Сравнительный анализ веток 3.0.x, 3.1.x и 3.2.x показал разнонаправленные результаты: ветка 3.1.x ограничена наличием открытых критических дефектов, ветка 3.2.x является актуальной, но недостаточно зрелой по сроку эксплуатации и числу патч-итераций, а ветка 3.0.x обладает наибольшей временной стабильностью, однако не является стратегически приоритетной по жизненному циклу.

Дополнительный анализ патч-релизов в рамках 3.0.x подтвердил отсутствие открытых критических дефектов на дату оценки; при этом 3.0.4 демонстрирует максимальный коэффициент закрытия дефектов, тогда как 3.0.6 рассматривается как наиболее практичный вариант внедрения внутри ветки за счет более позднего релизного среза и накопленного периода эксплуатации.

Комментарий к приложению:
По данным релизной истории ветки 3.0.x представленные патч-релизы содержат преимущественно исправления дефектов и не включают существенного нового функционала в рамках минорной версии. При этом релиз 3.0.5 был отозван, что дополнительно ограничивает его применимость как целевого для внедрения.

На дату оценки по всем рассмотренным патч-релизам 3.0.x отсутствуют открытые критические дефекты, что снижает риск блокирующих инцидентов при эксплуатации. Версия 3.0.4 демонстрирует наилучший коэффициент закрытия дефектов (94,2%), однако с практической точки зрения для внедрения предпочтительно использовать 3.0.6 как последний доступный патч ветки, аккумулирующий более поздний набор исправлений и прошедший длительный период эксплуатации после даты выпуска.
